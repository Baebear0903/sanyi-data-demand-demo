## 一、快速开始

### 方式 A：本地服务器打开（日常演示，推荐）

```bash
cd demo
pnpm install          # 首次
pnpm dev              # 开发模式 → http://127.0.0.1:5173
```

生产构建 + 预览：

```bash
pnpm build            # 类型检查 + 构建 → dist/
pnpm preview          # 预览 → http://127.0.0.1:4173
```

### 方式 B：离线单文件（发微信 / 拷 U 盘 / 断网演示）

```bash
pnpm build:offline    # → offline/数据需求管理-演示系统.html（约 2.3 MB）
```

**双击该 HTML 即可运行**，无需服务器、无需网络。已实测 `file://` 下零控制台错误。

> ⚠ **不要用 `file://` 打开 `dist/index.html`**。Vite 默认产物是 ES Module，`file://` 下会被浏览器 CORS 拦截
> （报错 `Access to script ... blocked by CORS policy`）。`dist/` 必须走 HTTP；需要双击打开请用 `offline/` 那一份。

### 方式 C：在线预览（GitHub Pages，已自动部署）

<https://baebear0903.github.io/sanyi-data-demand-demo/>

推送 `main` 即由 `.github/workflows/deploy-pages.yml` 自动重建并发布。

### 本机环境备忘

| 问题 | 现象 | 解决 |
| --- | --- | --- |
| 未装 pnpm | `pnpm: command not found` | 用 `corepack pnpm <cmd>` |
| corepack 缓存不可写 | `EPERM: mkdir '~/.cache/node/corepack'` | `export COREPACK_HOME=<开发仓库>/.tooling/corepack` |
| npm 源慢 | install 卡住 | `npm_config_registry=https://registry.npmmirror.com` |

一行式：

```bash
COREPACK_HOME="$PWD/../.tooling/corepack" npm_config_registry=https://registry.npmmirror.com corepack pnpm dev
```

> 若把本目录单独克隆到别处（没有 `../.tooling`），脚本会自动退回 corepack 默认缓存目录，上面这条也照常可用。

## 三、发布到 GitHub（只看代码，不看迭代文档）

本目录就是远端仓库 <https://github.com/Baebear0903/sanyi-data-demand-demo> 的**根目录**：
发布时只把 `demo/` 的内容推上去，**开发仓库根目录的迭代文档（需求文档 / 分析笔记 / 参考规格 /
参考资料 / 功能清单等）不进仓库**。

```bash
cd demo
pnpm deploy:github:preview     # 预演：打印将发布的文件清单与改动，不推送
pnpm deploy:github             # 正式发布：本地校验 + 构建 + 推送（幂等，内容没变则跳过）
```

- 脚本：`scripts/deploy-github.mjs`。它用 `git commit-tree` 把 `HEAD` 里 `demo/` 的目录树做成一次提交
  再推到远端 `main` —— 只发布 **git 已跟踪**的内容，`dist/`、`offline/`、`node_modules/` 天然进不去。
- 发布前会先跑 `check:recipes` + `vue-tsc` + 构建，任一失败即中止，远端不会出现半成品。
- `main` 一更新即触发 Pages 自动部署；用 `gh run list --repo Baebear0903/sanyi-data-demand-demo` 看进度。
- **不要用 `git push` 发这个仓库**：本地是「文档 + demo」的完整开发仓库，`git push` 会把迭代文档一起推上去。
  发布只走 `pnpm deploy:github`；本地 `main` 与远端 `main` 是两条线（这正是为了只发代码）。
- **一次性**：`pnpm deploy:github:fresh`（`--fresh-history`）用于把远端换成一个干净的初始提交
  （内容 = 当前 demo 树，不带旧历史）。只有在“收敛发布范围”时才需要跑一次。
- 若本机 `github.com:443` 连不上（常见于被解析到不可达 IP），脚本会自动改用固定可用 IP 重试；
  仍失败时见 `scripts/deploy-github.mjs` 头部「常见故障」。

| 层级 | 数量 | 说明 |
| --- | --- | --- |
| 根 | 1 | `## 1.2.6.3.1 数据需求管理`（清单原文为空，仅承载层级） |
| 模块 | 11 | `### 1.2.6.3.1.1 ~ .11` |
| 条目 | 57 | `#### 1.2.6.3.1.x.y` |

父行三列：**功能点名称**（清单编号 + 层级标签）/ **功能点描述**（清单原文逐字）/ **是否验收**。
其中**原文非空的 67 行有验收按钮**，原文为空的 2 行（根、`.8 知识问答管理`）不设按钮、不计入分母。

展开子行：

| 行类型 | 四列内容 |
| --- | --- |
| 条目行 | **角色** → **系统页面**（含菜单路径 / 详情页两级路径）→ **看得到什么 / 要做什么** → **对应示例数据** |

判断口径：**页面上能看见对应入口（按钮 / 区块 / 页签）即认为该功能描述被覆盖**，不要求现场把流程跑完，也不提供一键跳转。
所有子行文案都经 `scripts/check-recipes.mjs` 校验：必须能在对应页面源码里找到出处，示例编号必须真实存在于种子数据：

```bash

pnpm verify            # 覆盖校验 + 类型检查
node scripts/gen-feature-list.mjs   # 改完《功能清单.md》后重新生成覆盖行真源
```

### 重点实现（对应原文硬要求）

- **工作流自动化部署**：对已审核工单执行部署 → 10 步逐步日志 → **依据需求单字段与资源字段真实生成 API 接口定义**（含入参/出参表）+ 5 个相关文件 → 注册数据服务 → 写审计。实测可运行。
  - 部署队列按「**待部署 / 已部署 / 全部**」分列：部署成功的工单自动移出待部署队列，队列内显示「部署状态」（未部署 / 已部署 / 部署失败 + 时间）。
  - 生成的 5 个文件（交付说明 / 接口文档 / 调度配置 / 脱敏规则 / API 接口定义）**随部署记录归档**：部署记录「查看产物」可列出并预览全文，需求单详情「交付与授权」页签同步可见。历史记录无快照时由 `core/artifacts.ts` 按同一算法现场重建。
- **需求派发（审批通过后的实施入口）**：供数方在工作台「我的待办」看到「派发生产任务」并直达需求单详情；需求单管理页（切「全部」范围）行内也有「派发任务」→ 跳详情并自动打开派发弹窗。派发后需求单转「实施中」；**关联任务全部验证通过后需求单自动转「待验收」**；验证不通过退回的任务可「重新实施」（否则需求单永远无法完成闭环）。
  - **无生产任务的需求单也能闭环**：自助服务 / 电子邮件提交的需求单不派生任务，处理人可在详情页点「**标记实施完成**」→ 确认后转「待验收」；若单据确实有任务，则必须等任务全部验证通过（弹窗会列出未完成任务并给"去任务管理"入口）。
- **知识条目附件（原文 1.2.7.3.1.7.4）**：新建知识条目或条目详情均可 **上传本地文件 / 添加示例附件 / 移除**；`core/attachments.ts` 识别 pdf / word / ppt / txt / xlsx 等类型、生成可读大小并**抽取中文可检索文本**，文本并入 `contentText`，因此「附件内容检索」可即时命中。
- **知识问答归档**：问答管理新增「**待归档（n）**」分组，行内「选最佳答案并归档」会展开并定位到候选答案；选择最佳答案后自动生成知识条目（已发布）并把问答转为「已归档」。
- **自助服务权限矩阵可编辑**：平台管理员在「权限管理」点「编辑权限配置」后单元格变为复选框，保存即写回服务目录项 `allowedRoles`（字段级审计），服务目录可用项与统计卡同步刷新；其他角色为查看态并有明确提示。
- **预定义需求类别（原文 9.6）双入口**：服务台管理页新增只读对照面板（类别 / 需输入信息 / 激活流程 / 生成单据），统一受理台新增「预定义需求类别」列；配置与申请入口仍在自助服务管理（同名卡片列出 6 类完整定义）。
- **问题驱动发布（原文发布管理）**：问题单详情「创建发布申请」自动带入问题号 / 根因 / 解决方案生成发布单；发布管理新建弹窗支持「问题驱动」与 `?problem=` 带参预填；发布业务验证全部通过并完成审计后，**来源问题单自动闭环**。
- **变更实施计划调整**：变更列表、变更单详情、冲突分析结论三处共用同一「调整实施计划」面板（实施日期 / 实施者 / 分类 / 优先级 / 资源 / 计划说明），保存写字段级审计，并可「保存并重新分析冲突」；可调整状态与权限判定收敛在 `core/changePlan.ts`。
- **权限与演示基准时间一致性**：
  - 无「工作流自动化部署」权限（`flow.deploy`）时，部署按钮置灰并给出角色提示；变更单详情对无审批权限的角色同样置灰并说明（不再出现"按钮能点但报错/越权可点"）。
  - 单号日期、计划起止、部署日志时钟等**一律取演示基准时间 `NOW = 2026-01-27 10:30`**（`core/utils.ts` 的 `nowStamp / nowDate / nowIso`），不再混入真实系统日期。
- **变更风险评估**：基于 `cis.dependsOn` **反向遍历真实计算**影响链路（配置项 → 服务 → 租户），输出影响等级与建议，写回 `impact`/`riskLevel`。
- **变更冲突分析**：真实计算三类冲突 —— 时间窗（±1 天）、资源交集、服务依赖交集，写回 `conflicts`。
- **可视化变更窗口**：月历叠加变更 / 业务事件 / 发布三类日程，可切换月份。
- **事件决策树**：从根节点逐级选择，展示判定路径、结论、处置建议与建议分类，可「按此结论创建事件」。
- **事件知识推荐**：录入标题/描述时按分类关键字与知识库内容实时匹配推荐。
- **交付与授权**：订阅单按 API / 文件 / 实时切换字段；实时服务订阅**必填需求工单号并校验其存在与状态**；密钥 `appSecret` 脱敏展示、可补发/更换；推送记录含失败补推；敏感资源走 SFTP。
- **知识库**：分类树 + 标题/全文/**附件内容**三范围检索；富文本编辑器（含插图与 `[[知识:标题]]` 互引）；评分评论**自动通知维护责任人**；**问答归档为知识条目**。
- **评价双向可见性**：用数方/供数方视角切换，未审批的评价/反馈互不可见。
- **统计分析**：按事件（5 维度）/ 按用户（用方与运维双视角）/ **CMDB 视角**（每个配置项关联的事件、服务、租户与影响面）三视角。
- **审计中心**：统一承载变更/事件/问题/发布四类审计，行展开显示**字段级前后值对比**，单号可跳转原单；本页**只读**——留痕由各业务单据的真实写操作自动写入（需求受理审批 / 变更计划调整 / 服务权限调整 / 审批规则修改），审计中心只负责检索与导出。

## 十、边界声明（验收时请留意）

1. **上游系统按"对接态"模拟**：资源目录、数据服务、数据分类分级、能力开放门户、CMDB 均为内置 Mock 数据，
   不实现其内部功能 —— 对应原文对大数据平台类能力标注的「本项目不计费用」。
2. **原文未给出的数值均标注为演示假设**：SLA 时限、优先级矩阵、评价维度、停机窗口、部署耗时等；
   建设方案未提供量化性能指标，页面已用 `assume-note` 逐处标注。
3. **审计留痕为真实实现**：任何单据状态变更都写入字段级审计（前后值 + 修改人 + 时间），可在审计中心查看与导出；
   审计中心本身**只读**，不提供写操作入口——需要现场打样时，从业务侧真实操作产生留痕（见「审计中心」一条）。
4. **演示时间基准固定为 2026-01-27 10:30**：新增记录的创建/审批时间均落在该基准日，
   与种子数据保持时间一致性（不使用真实系统时间）。
5. **数据可重置**：顶栏「⋯ → 重置演示数据」随时恢复初始态。数据存于 localStorage，刷新保持操作结果。
6. **知识附件为前端模拟**：演示系统无后端文件存储，上传的附件只保留"文件名 / 类型 / 大小 / 可检索文本"四项
   （结构与真实实现一致，可用于演示原文要求的"允许把各类文件作为知识的附件 + 中文附件内容搜索"）；
   二进制文件（pdf / word / ppt / xlsx）尽力抽取可读文本，不可解析时退化为按文件名参与检索，页面对此有说明。
